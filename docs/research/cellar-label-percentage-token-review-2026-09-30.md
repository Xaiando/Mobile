# Cellar label percentage-token review

30 September 2026. This is a parser correction, not native camera/OCR acceptance.

The previous two-digit percentage search could extract `5%` from `100.5%` or `130,5%`, then offer it as an alcohol clue. It also accepted the unsigned part of `-12.5%`. The normal editor still required explicit acceptance and did not auto-save these suggestions, but the proposed value could be wrong.

`lib/core/journal/label_proposal.dart` now captures a whole numeric percentage candidate before validating one unsigned value. Signed values, ranges, malformed comma/period combinations, more than two decimal places and values outside the existing `0 < ABV <= 30` contract are withheld. Multiple percentage candidates remain ambiguous, including a valid value beside an invalid one. Percentage digits cannot become a vintage; a separate `2019` and ordinary `13.5%` on the same label still retain both clues. Valid period/comma values and text such as `alc.13.5%vol` remain supported. Names and bottle identity are still entered and confirmed by the learner.

Five new focused tests supplement the existing synthetic corpus and ambiguity tests in `test/core/journal/label_proposal_test.dart`. They cover numeric-tail errors, signs including Unicode minus, malformed groups, numeric ranges, preserved bounds, ordinary surrounding label text, ambiguous percentages and year-like percentage tokens. Formatting and diff checks are complete; root owns the actual Dart test and integrated-suite runs. Synthetic parser checks cannot establish recognition accuracy.

The historical [0.22.0 cellar gap note](sommelier-cellar-and-service-gaps.md) predates the implemented scanner. Current code has private label/glass photo storage, explicit proposal acceptance, unsupported-platform manual fallback and Android lost-pick recovery. Backups now enforce aggregate photo, row and encoded-file limits in `UserDataBackup`; the older scanner plan's claim that import bounds are missing is historical.

Frozen PR44 head `a77df27bfb27f5a3cc39337a1a37b996cd68b945` passed [run36633382422](https://github.com/Xaiando/Mobile/actions/runs/36633382422), including Windows integration/build, Chromium web smoke, Android builds and an unsigned iOS build. Its 1,293-test final log is preserved separately from newer local changes. The web scanner smoke uses manual label text and file selection. None of those jobs observes native capture, OCR, permission handling or device file cleanup.

The bounded next acceptance action is to run one recorded session on a physical Android device and one on an iPhone at a fixed candidate commit: capture in two orientations; cancel a pick and deny/allow permissions where the OS prompts; import a native iPhone HEIC image; scan a Latin label offline; confirm/correct the proposed vintage/ABV; restart and verify both saved photos; test Android interrupted-pick recovery; and verify backup/restore plus guarded temporary-file cleanup. Record device model, OS, build/commit, inputs, timestamps and each actual outcome. Until this happens, those outcomes remain unknown. The pinned picker explicitly calls for [real-device HEIC checks](https://pub.dev/packages/image_picker); [ML Kit's platform bridge](https://pub.dev/packages/google_mlkit_text_recognition/versions/0.17.1) is mobile-only. The pinned Android dependency is the [bundled Latin recognizer](https://developers.google.com/ml-kit/vision/text-recognition/v2/android), so model packaging supports offline use in principle; an offline capture/OCR result still requires observation on a device.
