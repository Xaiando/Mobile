# Independent runtime review

Read-only review on 27 September 2026. No SDK/source/Git changes. Reviewed root's teaching requirement/progress changes and repaired rehearsal runtime. This report describes the code at review time; root is still authoring the published requirement bank.

## Concrete findings

1. **P2 — Home still uses optional atlas facts in its progress bar.** `lib/features/progress/wset_progress_card.dart:69–79` reads `level.counts`, while detail correctly uses `level.milestoneCounts` at `lib/features/progress/wset_progress_screen.dart:127`. When required facts are mastered but optional material is new, detail can show the study milestone complete while Home's level bar remains far below 100%. Use milestoneCounts consistently for the principal level bar and optionally add a separately labelled total-material line. Regression: required 1/1 mastered, optional 0/99; Home and detail principal bars must agree while optional material remains visible.

2. **P2 — Restored rehearsal deadlines are only partially validated.** `lib/core/rehearsal/rehearsal.dart:230–291` checks deadline after start and completion after start, but accepts a Level 1 deadline 30 hours after start, an expired completion before/after its deadline, or a submitted completion beyond deadline. Those states cannot be produced by normal repository writes; accepting them makes corrupt backup snapshots silently alter the promised timer/history. Validate exact preset duration, expired completion equal to deadline, submitted/abandoned completion no later than deadline, and portable explicit UTC timestamps. `DateTime.parse` accepts timezone-free/local strings and calendar overflow, so validate canonical saved timestamp spelling as well. Regression fixtures should mutate an otherwise valid saved attempt and fail visibly, while valid old snapshots/backup round trips remain unchanged.

3. **P2 — Settings-key/payload identity is not checked.** `RehearsalRepository._load` at `lib/core/rehearsal/rehearsal.dart:346` retrieves key A then accepts a JSON attempt whose `id` is B. Current/pointer reads can return a different attempt and later answer calls address a missing/different key. Verify payload ID matches the requested key ID. History should also check sanitized key/payload agreement rather than parsing arbitrary mismatched entries. Strong UUID shape validation is preferable to a loose 36-character hex/hyphen class. No SQL injection issue is present; this is corruption/recovery consistency.

4. **P2 — Explanatory requirements can list map-only formats.** `WsetEvidenceDimension.validate` at `lib/core/progress/wset_requirements.dart:90–98` accepts every registered mode for every kind. The repository rightly refuses `LOCATED_IN` facts for non-location dimensions (`wset_progress.dart:298–309`), but a non-location grape-permission/planting fact may serve `map_grape`; a malformed `production` or `quality_assessment` dimension requesting `map_grape` would therefore count as available at `:394–400`. Disallow map-only modes for dimensions intended to explain/evaluate (environment, production, style, quality_price, vine, winery, description, quality_assessment, ageing); retain legitimate map practice for location/grapes. Exact source-grounded fact assignment still needs editorial review; code should prevent this simple format loophole. Regression: malformed explanatory map-only dimension fails, while ordinary location/grapes map support remains available.

5. **Low-priority clarity — blank prose can be self-checked as supporting every criterion.** `RehearsalRepository.selfAssess` at `lib/core/rehearsal/rehearsal.dart:516–522` checks finish/criterion IDs but not whether the corresponding prose exists. The UI enables these checks for blank finished written answers. These are explicitly subjective declarations, so this does not confer an official mark; nevertheless, any future progress activity must require nonblank saved prose and avoid counting checked empty answers as written practice. Prefer disabling criteria on unanswered prose or retaining an explicit unanswered status. Test both blank and nonblank answers.

## Verified safeguards and non-findings

- Unknown required IDs fail visibly. Expired/unmapped required IDs remain in the required denominator and become unavailable, rather than disappearing (`wset_progress.dart:293–296,378–409`). Current planner membership/depth/generation gates govern availability.
- Per-level duplicate requirement IDs, duplicate dimension kinds, duplicate IDs within a dimension and unknown modes are rejected. Cross-requirement reuse of a fact is deduplicated in the required union and is legitimate; each associated dimension must actually have one of its served modes.
- `LOCATED_IN` cannot satisfy non-location explanatory evidence, and non-location facts cannot satisfy location evidence. Exact IDs replace broad selector counts. This does not by itself establish editorial sufficiency.
- Required and optional denominators are separated. Optional material does not block `appLevelComplete`, while unavailable required facts and unreviewed requirements do. Scope completeness still gates milestone completion. Published scope flags remain false during authoring.
- Shared FSRS thresholds/date/lapse/decay behavior and independent self-reported exam settings are preserved. Requirements check format availability, not separate format mastery; labels should continue to describe fact-memory support rather than practical competence.
- Rehearsal start enforces the active WSET track and current mapped canonical facts; optional blueprint sampling is unique and fails shortages instead of shortening. Full preset counts/durations are enforced at bank/start time.
- Rehearsal persisted keys now sanitize UUID hyphens. Answers and finalization enforce expiry transactionally; repeated finish returns one persisted result. No automatic FSRS or exam-pass writes occur. Historical prompt/options/rubric snapshots remain independent of later bank changes and existing backup exports their settings.
- Corrupt current selection can be reset without deleting saved history bytes. One corrupt historical row currently suppresses the best-effort history list; root may improve recoverable history reporting later.

## Proposed separate paired physical tasting slice

Owned new paths: `lib/core/tasting_pair/`, `lib/features/tasting_pair/`, `test/core/tasting_pair/`, `test/features/tasting_pair/`. Root owns JSON/grids/routes/navigation/progress. A small explicitly authorized helper in `GuidedTastingRepository.start` is needed: `makeCurrent:false` (or `startDetachedPhysical`) creates a physical guided session without overwriting/blocking the standalone guidance pointer. This should retain active-level checks and the same evidence/grid snapshot logic.

Start one Level 3 pair atomically: two blind physical guided sessions, one UTC startedAt/deadline exactly 1,800 seconds, pair UUID/settings snapshot/current pointer. Use safe settings names. Timer continues offscreen/closed; no reset pause. Pair answer methods enforce their shared deadline and update the existing guided observation/evidence storage. Separate Wine 1/Wine 2 tabs share a persistent timer; optional journal linkage is supported without revealing the wine during the attempt.

Manual finish or expiry stores immutable observation/evidence snapshots for both wines and one stable completion reason. Unanswered fields remain explicitly incomplete; finishing an attempt must not invent a tasting grade, mark its guided evidence complete, change FSRS, or set an official pass. Where all guidance fields are complete, guided completion may also be recorded. Later legacy edits may reopen the guided session but cannot rewrite the finished paired attempt snapshot. Backup/restart/history and duplicate concurrent finish tests are required.

This module would be labelled original paired tasting rehearsal, with transparent evidence review rather than an objective unknown-wine score. Completion of this app activity is distinct from practical tasting competence and official assessment.
